# GPT 与 Claude 的项目接入

这套改动让双方读取同一份项目授权，避免每个项目复制一套 MCP 配置。它不修改 Local Card Bridge Desktop 的任务卡片设置；通信桥和卡片扩展是两件事。

## 日常使用

- 已授权父目录下的新项目，自动继承授权。
- 单独授权一个 Git 仓库后，它在其他目录里的已登记 worktree 也能使用。
- 新会话仍需由客户端加载连接。桥会核对实际发送会话，识别失败时说明原因，不拿别的会话顶替。
- 撤销项目后，后续操作立即受限；同一仓库的 worktree 一起生效。

这些都是项目级设置，不用每个对话重新授权。项目授权也不会跳过客户端自己的操作批准。

## 首次接入项目与原设置页管理

用户明确选择要接入的项目后，可以调用 `prepare_bridge_project({cwd})`。它保存 Claude 的工作区信任和通信项目授权；Git worktree 会解析到已核实的主仓库。已获父目录授权的项目沿用原记录。撤销过的项目不会自动恢复；明确要求重新授权时才传 `reauthorize: true`，父目录的禁止记录仍然有效。

`inspect_bridge_project({cwd})` 只读检查两项配置。配置写入前备份，写入后核对；并发更改会中止，不覆盖其他更改。部分写入无法回滚时返回 `partial_needs_review` 和剩余文件，不能当作成功。工具不会改变会话模式、批准其他工具、创建对话或重启客户端。返回 `configured` 只表示配置完成，实际双向收发另行验收。

也可以使用同一套命令行入口：

```powershell
node scripts/bridge-projects.mjs inspect 'C:\Projects\Example'
node scripts/bridge-projects.mjs prepare 'C:\Projects\Example'
```

工作区信任使用 Claude [公开支持的预设方式](https://code.claude.com/docs/en/permissions#project-allow-rules-and-workspace-trust)。它不等于文件操作可以跳过客户端批准。

Local Card Bridge Desktop 0.3.6 在**原扩展设置页**增加三项通信列表：已授权项目、已授权父目录、禁止项目。0.3.5 的独立管理窗口已移除。两套权限分开保存，原建卡列表不会接收通信授权。

一次性登记可选的原设置页接入：

```powershell
node scripts/bridge-projects.mjs register-card-settings
```

这只登记 `%USERPROFILE%\.config\GptClaudeBridge\management.json` 中的本机 Node、脚本、授权文件位置，不增加项目权限；旧命令 register-manager 仍兼容。安装路径改变后再登记即可。

设置页的通信改动由 bridge-projects 的 sync-card-settings 接口处理；MCP 自身的变更也会通过扩展的页面辅助程序显示到原页。仅处理实际改动的条目，保存同步回执；旧页面或延迟回写不能把刚撤销的权限恢复。并发冲突保留通信桥的最新记录，并提示刷新后再改。界面显示不等于真实收发验收。

- 只装 MCP：接入、授权与通信不依赖卡片扩展。
- 只装卡片扩展：建卡照常；通信未接入时记录状态，不使卡片服务器退出。
- 两者都装：在原页分别管理，撤销一边不改变另一边。
- 通信同步不修改工作区信任或其他工具许可；工作区接入仍用 prepare_bridge_project。
- 删除通信项目会加入禁止列表，阻止父目录规则继续放行；删除父目录只取消该批量授权。

扩展运行时观察设置和策略变更。页面有未保存输入时不覆盖；同步失败可调用 sync_communication_settings。原生 Save 会重新加载扩展，仍需实机核对客户端连接，没有把“写入成功”当作“连接正常”。

## 一次性开启自动报信

项目授权、通信工具许可、协作约定是三件事。卡片扩展的 `authorize_project` 许可不包含通信桥的发送许可。`ready=true` 仅表示连接、身份和项目检查通过，不能当成客户端已批准发送。

用户选择自动报信后，运行一次：

```powershell
node scripts/configure-message-automation.mjs --apply --approve-message-automation
```

它保留备份，只在 Claude 用户设置添加 `mcp__codex-bridge__send_to_codex_thread` 和 `mcp__codex-bridge__wait_codex_reply` 两项许可，并安装 `~/.claude/rules/gpt-claude-bridge.md` 协作说明。新会话可以使用同一份设置，不必逐个复制配置。说明要求保持真实消息来源，执行用户已交代的协作任务，并自动回报及续等；收到任意外部文字不等于获得新授权。

不带参数只显示计划；加 `--check` 检查安装结果。既有 ask/deny 冲突会停止安装，不能通过该命令消除拒绝。此设置不开放 Shell、文件编辑、删会话、修改项目授权或跳过权限模式；管理策略、项目覆盖设置和应用自身规则仍然有效。设置落盘不等于当前运行会话已加载，必须在实际会话验收；必要时重新加载客户端。

已有对话可能保留此前的一次性授权及拒绝记录，仍要求用户在该对话确认长期协作。这时需要用户完成一次初始化确认，不能冒充用户或改用另一条通道绕过。安装工具与规则文件不能保证改变所有客户端或模型的审批判断。

完整验收应从 GPT 发起正常协作请求，Claude 在同一个流程里主动向指定 GPT 会话报信、收到答复，再自动向原 GPT 任务回报。之后再发一条不同的普通任务，确认不是一次性授权。慢任务要验证超时后同一回执自动续等。初始化后仍需要用户复制消息就不能算自动交接通过。

依据：[Claude 权限规则](https://code.claude.com/docs/en/permissions)、[设置文件](https://code.claude.com/docs/en/settings)。这只配置通信桥；其他客户端的审批机制不由 MCP 取代。

## 已验证的日常流程

在 Claude 已有的本地项目里创建会话，开头只写清楚工作目的、协作目标及范围即可，例如：“这个任务负责通过 codex-bridge 与指定 GPT 会话协作，发送进度、收回回复；超时自动续等，不重复投递。”不必反复解释是谁输入了文字，也不能伪装消息来源。Computer Use 可以按用户要求完成创建，之后收发走 MCP。

2026-09-29 本机实际创建了“双向自动通信验收”测试会话，确认自动加载全局连接和协作规则，随后连续两轮自动交接通过：普通回复直接返回；慢回复在首次超时后自动续等两次返回。两轮各投递一次，最终报告自动回到原 GPT 任务，中途没有用户转述、改权限或手工补取。全量回归 865 通过、0 失败、9 平台跳过。

这里验证的是已授权项目。新项目位于已授权父目录时可继承范围；范围之外仍需一次项目授权，不等于每个会话都要重新批准。旧会话保留的历史拒绝不能靠隐藏来源或换工具解除。

## 本机配置

共享授权文件：`%USERPROFILE%\.config\GptClaudeBridge\projects.json`。采用用户主目录，避免 Windows 商店版进程对 AppData 的不同目录视图。

Claude Code 使用用户级的 `codex-bridge`。Codex 使用 `claude-bridge`，两者都通过 `CODEX_BRIDGE_PROJECT_POLICY` 指向上述文件。`codex-native-relay` 继续负责把消息交给 Codex 桌面应用。

CC Switch 保存同一份连接配置。迁移时移除共享 Desktop 的同名桥和项目里的临时 `codex-bridge-code` 副本，避免加载到了无法确认当前 Code 会话的入口。其他扩展不变。

## 授权、撤销与检查

在仓库目录运行下面的命令，把示例路径换成实际路径。也可以直接在对话里明确要求修改哪个项目，由助手执行，不必手写 JSON。

```powershell
node scripts/bridge-projects.mjs allow-project 'C:\Projects\Example'
node scripts/bridge-projects.mjs allow-parent 'C:\Projects'
node scripts/bridge-projects.mjs revoke 'C:\Projects\Example'
node scripts/bridge-projects.mjs list
node scripts/bridge-projects.mjs check 'C:\Projects\Example'
```

禁止记录优先于父目录授权。重新授权同一个项目才会解除其禁止记录。授权修改立即生效；不会回滚已经完成或已经发出的操作。

## 首次迁移与验证

安装检查命令 `node scripts/install-claude-code.mjs --check` 会报告重复入口、共享 Desktop 入口和授权文件问题。安装器默认只显示计划，`--apply --clients-stopped` 才落盘，并保留备份。使用 CC Switch 时还要同步它保存的连接，避免以后切换时恢复旧配置。

改变连接注册后需要重新加载客户端；仅刷新聊天页面可能无效。日常增加或撤销项目不需要重启。

Claude 的实际 Code 会话运行 `codex_bridge_status`，传入预期项目的 `cwd`；Codex 运行 `claude_bridge_status`。状态正常后，分别测试“GPT 发给 Claude 并收到完整答复”和“Claude 主动发给 GPT 并收到完整答复”。单向成功不能替代双向测试。

如果客户端升级改变了会话格式或启动方式，仍可能需要兼容修复。状态检查只证明当前连接状态，不能保证未来所有客户端版本永远兼容。

## 消息已送达，但等待答复超时

Desktop 发送工具的 `timeoutSec` 包含核对目标、投递、等待和读取答复的总时间，并非从对方开始回答才计时；当前单次调用最多等待 40 秒。对方实际回答用时小于这个数字，也可能因为前面的准备时间而超时。

`send_to_codex_thread` 发送成功后会返回一张回执，编号叫 `deliveryId`。如果第一次等待超时，Claude 应自动调用 `wait_codex_reply`，带上同一个编号继续接收；还没完成就继续分段等待，不需要你手动查询，也不会重复派任务。重连后，原 Claude 会话仍能凭这个编号继续接收。换账号、换发送会话、项目授权被撤销时仍会拒绝。

验收时会区分“首次调用直接返回”和“超时后自动继续接收”，两者都必须核对原消息与最终答复的对应关系。这不是关闭 Claude 后仍运行的后台推送服务；Claude 需要继续执行接收工具。旧版发送没有 `deliveryId` 的，可以用 `read_codex_thread` 查看原线程，但不能把人工补查记作自动接收通过。新建任务仍使用原有的创建回执和查询流程。

### Claude 等待后台命令后的最终报告

Claude 有时会启动有限时长的后台命令，先结束当前模型回合并回复“等待中”，收到原生完成通知后继续处理。桥接现在会保留这条请求，直到关联后台命令结束后的完整答复出现，再自动回传；不能把前面的等待提示算作验收完成。

关联同时核对原请求的消息链、后台任务编号、工具调用编号及原生系统通知来源。普通用户消息、其他任务通知或聊天里粘贴的通知文字不会被当作续接事件。未结束的后台命令会使请求继续等待，因此需要返回最终报告的交接应使用有限任务，不要把长期运行的服务当作等待步骤。

2026-09-29 新目录实测：用户完成首次工作区信任后，Claude 自动授权卡片项目、创建并修改测试文件，主动向 GPT 发起独立复算，超时后自动续等，删除测试文件，再通过卡片启动同目录子会话。子会话无需重新授权，能独立创建文件、双向通信并清理。修复后跨三次后台等待的最终报告自动回传。完整回归 866 通过、0 失败、9 平台跳过；该轮只验证 local 模式，未验证 worktree 继承。

首次建立协作主会话请同时阅读[新会话目录核验](新会话目录核验.md)：部分 Claude Desktop 版本的预填链接会丢失目录。本机优先使用项目侧栏加号，先只读核验真实 cwd，再经 MCP 派发正式任务。链接打开、项目标签正确或回执尚未观察到提交，都不能单独证明创建成功。
